# 键盘认证修复（2026-11 HyperOS OTA 后键盘失效）

2026 年 11 月的 HyperOS OTA 更新了键盘固件。更新后，Linux 侧官方键盘（Pogo Pin）的按键与触控板失效，而背光与麦克风指示灯正常。原因：新键盘固件只接受**在线密钥**路径的认证 token，而 Linux 侧 devauth 服务仍按旧的**离线路径**应答，token 被键盘拒绝后其输入通道被暂时压制。

本指南把认证服务切换到在线路径并补齐密钥文件，使键盘恢复。**全程不需要改动 Android 系统**，认证为纯本地计算，不依赖任何服务器。

## 症状自查

符合以下全部特征，即为本文针对的问题；否则无需本指南：

- 背光可调、麦克风指示灯正常，但**按键与触控板无输入**
- `journalctl -u sheng-devauth` 中出现 `devauth command error 0 status 0xaa000018`
- 重新插拔键盘可短暂恢复，一段时间后再次失效

## 原理简述

- 键盘 MCU 约每 61 秒向平板发起一次认证挑战。**附着后输入立即可用**（认证不是输入的门禁）；挑战长期得不到有效应答时，固件会压制输入通道，重新插拔吸附会重置计时——这就是"重插能暂时续命"的来源。
- token 由平板 TEE 内的 devauth TA 计算：`token = AES-128-ECB(challenge, 密钥)`。密钥有两条路径：**离线**（key_meta `0x00000002`，来自 RPMB 主密钥）与**在线**（key_meta `0x40000002`，per-UID 派生键）。本次 OTA 后键盘固件只认在线路径。
- 在线密钥库（keyChain）由 Android 侧认证时写入 **persist 分区**（Android/Linux 共享同一分区）。Linux 侧服务需要把它复制到自己的存储目录。

## 前提

- 已安装本发行版（含 `sheng-devauth`、`firmware-xiaomi-sheng`、`xiaomi-sheng-fingerprint` 三个包）
- **Android 侧键盘可正常使用**（OTA 后至少在 Android 插拔过一次键盘，以刷新密钥文件；单 Linux 用户请先启动一次 Android 完成此步）
- root（sudo）权限

## 修复步骤

以下命令均在 Linux 侧执行。

### 步骤 1：获取新版 TA 分段并合并

devauth TA 以高通分段格式（`devauth.mdt` + `devauth.b00`…`devauth.b08`）随系统固件分发，需合并为单个 `.mbn` 后供 Linux 侧加载。来源二选一：

- **方式 A（推荐，需已 root 的 Android）**：在 PC 上逐段拉取：

  ```bash
  adb shell "su -c 'cat /vendor/firmware_mnt/image/devauth.mdt'" > devauth.mdt
  for s in b00 b01 b02 b03 b04 b05 b06 b07 b08; do
    adb shell "su -c 'cat /vendor/firmware_mnt/image/devauth.$s'" > devauth.$s
  done
  ```

- **方式 B（未 root）**：从对应版本的官方线刷包中提取同路径的 `devauth.*` 文件（在各分区镜像内查找）。

将脚本保存为 `merge_devauth.py` 并在与分段文件相同的目录执行：

```python
#!/usr/bin/env python3
"""按 ELF 段表正确合并 devauth 分段（切勿直接 cat 拼接）"""
import struct, sys
mdt = open('devauth.mdt', 'rb').read()
phoff = struct.unpack_from('<Q', mdt, 0x20)[0]
phesz = struct.unpack_from('<H', mdt, 0x36)[0]
phnum = struct.unpack_from('<H', mdt, 0x38)[0]
total, segs = 0, []
for i in range(phnum):
    o = phoff + i * phesz
    off, filesz = struct.unpack_from('<QQ', mdt, o + 8)[0], struct.unpack_from('<Q', mdt, o + 24)[0]
    segs.append((i, off, filesz)); total = max(total, off + filesz)
out = bytearray(total); out[0:len(mdt)] = mdt
for i, off, filesz in segs:
    data = open(f'devauth.b{i:02d}', 'rb').read()
    assert len(data) == filesz, f'b{i:02d} 大小 {len(data)} != 段表 {filesz}'
    out[off:off + filesz] = data
open('devauth.mbn', 'wb').write(out)
print(f'合并完成: devauth.mbn {len(out)} 字节')
```

⚠️ **不要**把 `mdt` 与 `bXX` 直接 `cat` 拼接——段间存在对齐空洞，直接拼接会得到非法镜像（尺寸也会明显小于正确值）。

### 步骤 2：部署 TA

```bash
sudo cp /usr/lib/firmware/qcom/sm8550/sheng/devauth.mbn /usr/lib/firmware/qcom/sm8550/sheng/devauth.mbn.bak
sudo cp devauth.mbn /usr/lib/firmware/qcom/sm8550/sheng/devauth.mbn
```

合并结果约为 143 KB；若你的分段尺寸不同以脚本输出为准。

### 步骤 3：给认证服务打补丁（切换到在线路径）

将脚本保存为 `patch_devauth_online.py` 并执行 `python3 patch_devauth_online.py /usr/bin/xiaomi_devauth /tmp/xiaomi_devauth.online`：

```python
#!/usr/bin/env python3
"""xiaomi_devauth 二进制补丁：离线路径(0x2020/keymeta 00000002) -> 在线路径(0x2010/40000002)"""
import struct, sys
src, dst = sys.argv[1], sys.argv[2]
data = bytearray(open(src, 'rb').read())
hits = [o for o in range(0, len(data) - 3, 4)
        if (struct.unpack_from('<I', data, o)[0] & 0xFFFFFFE0) == (0x52800000 | (0x2020 << 5))]
assert len(hits) == 1, f'MOVZ 0x2020 命中 {len(hits)} 处（期望 1）'
off = hits[0]; rd = data[off] & 0x1F
struct.pack_into('<I', data, off, 0x52800000 | (0x2010 << 5) | rd)
print(f'[1] 命令号 0x2020 -> 0x2010 @ {off:#x}')
hits = []
i = data.find(b'00000002')
while i != -1: hits.append(i); i = data.find(b'00000002', i + 1)
assert len(hits) == 1, f'keymeta 串命中 {len(hits)} 处（期望 1）'
data[hits[0]:hits[0] + 8] = b'40000002'
print(f'[2] keymeta 00000002 -> 40000002 @ {hits[0]:#x}')
open(dst, 'wb').write(data)
print(f'写出: {dst}')
```

脚本只改 2 个字节，任何异常（命中数不为 1）都会拒绝写盘。部署：

```bash
sudo cp /usr/bin/xiaomi_devauth /usr/bin/xiaomi_devauth.bak
sudo cp /tmp/xiaomi_devauth.online /usr/bin/xiaomi_devauth && sudo chmod +x /usr/bin/xiaomi_devauth
```

### 步骤 4：搬运密钥文件

Android 侧认证时会把密钥文件写进 **persist 分区**（Linux 侧以只读方式挂载在 `/mnt/sheng-persist`），而 devauth 服务实际读取的是 rootfs 上的 `/mnt/vendor/persist/data/devauth/`，需要手动复制：

```bash
sudo mkdir -p /mnt/sheng-persist
mount | grep -q sheng-persist || sudo mount -o ro /dev/disk/by-partlabel/persist /mnt/sheng-persist
sudo mkdir -p /mnt/vendor/persist/data/devauth
sudo cp /mnt/sheng-persist/data/devauth/* /mnt/vendor/persist/data/devauth/
```

正常应看到三个文件（合计约 700 字节）：keyChain（约 84 B）、`devauth_load_key`（约 579 B）、`devauth_uid_list`（约 68 B）。密钥按设备加密存储，**不可跨设备拷贝**。

### 步骤 5：重启服务并验证

```bash
sudo systemctl restart sheng-devauth
# 重新插拔键盘
journalctl -u sheng-devauth -n 20
```

**成功标志**：挑战应答后只有 `Sent pad token to kernel driver!`，没有 `devauth command error` 行；按键与触控板恢复。

### 建议：锁定相关包

本文修改的两个文件分属 `sheng-devauth` 与 `firmware-xiaomi-sheng` 包，包升级会覆盖它们：

```bash
sudo apt-mark hold sheng-devauth firmware-xiaomi-sheng
```

需要升级时先 `apt-mark unhold`，更新后重做步骤 2、3，再重新 hold。

## 退路：关闭认证服务，以重插维持使用

如果修复步骤受阻，或暂不打算折腾，可以直接关闭认证服务，利用键盘固件的宽限机制维持使用：

```bash
sudo systemctl mask sheng-devauth
# 恢复认证时：sudo systemctl unmask sheng-devauth，然后按本文修复
```

此状态下的行为：

- **附着后输入立即可用**，无需认证；
- 无应答的认证挑战持续一段时间后，固件会压制输入通道——表现为背光/麦克风灯正常但按键失效；
- **重新插拔吸附即恢复**，并重新开始计时；
- 重启行为随键盘固件版本而异：**2026-11 OTA 后的新固件实测重启后无需重插**（开机附着即开始宽限计时）；旧固件按社区文档记载需重新插拔一次以触发认证。你的固件属于哪种行为，重启试一次即可确认。

⚠️ 宽限时长没有保证，随键盘固件版本可能变化（2026-11 OTA 后实测可用，通常可持续数分钟至更久）；介意频繁重插的话仍建议走完整修复流程。

## 后续维护

| 场景 | 处理 |
|------|------|
| HyperOS OTA 后键盘再次失效 | 在 Android 插拔一次键盘刷新密钥 → 重做步骤 1（若分段有变）与步骤 4 |
| 重装/更换 rootfs | 三处修改全部丢失，按本指南从头重做 |
| 认证服务器不可用 | 不影响——token 为纯本地计算，无服务器依赖 |

## 故障排查

| 现象 | 原因 | 处理 |
|------|------|------|
| `status 0xaa000018` | keyChain 文件缺失或为空 | 确认 Android 侧已认证过；重做步骤 4 |
| `status 0xaa00000d` | uid_list 写失败 | 良性，可忽略 |
| `status 0xaa000004` | 命令号/版本错误 | 步骤 3 补丁未生效，检查二进制 |
| 背光、麦克风灯也不正常 | 触点/驱动层问题，与认证无关 | 检查 Pogo 触点与内核驱动 |
| 服务 inactive | 依赖服务未起 | 确认 `qteesupplicant.service`（来自 `xiaomi-sheng-fingerprint` 包）已启用 |
| 重插能短暂恢复、随后复发 | token 持续无效（密钥代差） | 按"OTA 后再次失效"处理 |

## 附注

- **2026-11-26 实测**：新键盘固件（2026-11 OTA 后）下，主路（完成认证修复）与退路（关闭认证服务）在设备重启后均无需重新插拔键盘，开机附着即恢复。旧社区文档"每次重启后都需要重新插拔 Pogo Pin"描述的可能是 OTA 前**旧固件**的行为（认证需插拔事件触发）。对这一新旧差异的机制猜测：新固件附着即启用输入（宽限先行），认证异步跟进，pad 重启重新枚举即重新开始宽限计时；旧固件则需插拔事件才发起认证。该差异仅经单台设备验证，不保证所有设备/固件版本一致，以实际表现为准。
- 本指南基于对 devauth 认证栈的分析（2026-11，HyperOS OS3.0.7.0 OTA 后的键盘固件），适用于 sheng 全型号；不适用于其他机型（TA 签名按设备信任链绑定，且旧代际键盘无此认证机制）。
- 同款认证方案如在其他设备/固件版本上出现类似问题，修复思路一致：确认键盘期望的 key_meta 路径 → 用正确的 TA + 对应路径应答 → 保证密钥文件在服务可读的存储位置。
